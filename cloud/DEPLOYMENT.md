## 테스트 사용자
`cloud/test-users.sql` 적용. 테스트 사용자 모드는 현재 회원에게 저장하며 실제 로그인 계정을 바꾸지 않습니다. 별도 회원별 커서·게시물 캐시와 개인 분석으로 수집합니다. 새로고침당 구독 전체 최대 1개 게시물, 실행 시각·비활성·영상·분석 한도 조건은 유지합니다. 예약 작업도 한 번에 한 게시물만 처리합니다. 초기화는 확인 문구 입력 후 RPC 트랜잭션으로 본인의 테스트 커서·캐시·대기 작업과 분석 목록 기준시각을 초기화합니다. 원본 분석과 Google 등록 추적은 보존하므로 기존 일정 삭제는 내 일정에서 가능합니다. 초기화 후 동일 게시물 재분석 시 새 이벤트가 생성될 수 있으므로 반복 테스트 전 내 일정에서 이전 테스트 일정을 삭제하세요.

새 테스트 수집 계정의 최초 `next_due`는 요청의 실행 판단 시각으로 명시합니다. DB의 기본 `now()`가 요청 시작 이후 생성되어 첫 실행을 `not_due`로 건너뛰던 문제를 방지하며 기존 계정의 대기·오류 재시도 시각은 변경하지 않습니다. 수동 ‘지금 수집’도 실제 처리 여부와 다음 확인 시각을 반환하고, 건너뛴 요청을 수집 완료로 안내하지 않습니다.

2026-11-14 전체 기능 재검토: 비어 있는 계정은 마지막 확인 시각·다음 실행 시각을 저장하고 게시물 처리 건수를 올리지 않습니다. 예약 실행은 다음 계정을 계속 확인하되 실제 게시물 처리는 기존과 같이 최대 1개입니다. 해지한 구독의 테스트 커서는 진행상황에서 제외하고 비활성 구독은 오류 대신 꺼짐으로 표시합니다. 전체·회원별 수동 일일 한도는 한국 날짜로 통일했습니다. 구독 해지 후에도 본인의 내보내기 기록이 있는 일정은 열어 검토할 수 있으며, 다른 회원의 내보내기 기록은 사용하지 않습니다. Google 검토 링크의 분석 ID는 로그인 왕복 동안 탭 세션에 보관하고 서버에서 접근 권한을 다시 검증합니다. 여러 날 일정은 웹에서도 시작일부터 마지막 날까지 날짜 조회·표시에 포함됩니다.

`cloud/preserve-sync-on-reset.sql`을 운영 DB에 적용해 초기화 함수가 이미 접수된 캘린더 작업을 삭제하지 않도록 변경했습니다. 실제 회원의 초기화를 실행하지 않고 함수 정의에서 보존 여부를 확인했습니다. 기존 회원·일정·분석 데이터는 초기화하거나 삭제하지 않았습니다. 이번 회귀 테스트 81개와 빌드·번들 문법 검사가 통과했고 npm 의존성 취약점은 0건입니다. 실제 회원 탈퇴·새 OAuth 동의·휴대폰 수신 재시험은 이번 검토에서 실행하지 않았습니다.


## 운영자 기기 진단
`cloud/operations.sql`을 적용하고 `OPERATIONS_ADMIN_IDS`를 검증된 운영자 Supabase UID로만 설정합니다. `/api/operations`는 일반 회원에게 본인 필터를 강제하고 운영자에게만 최소 기기·요청 상태를 제공합니다. 이메일·일정·토큰·회원 UID는 반환하지 않습니다. 기기는 로그인 후 및 활성 화면에서 60초마다 상태·오류 분류를 전송합니다. 기존 브라우저도 새 코드를 불러오도록 새로고침해야 합니다.


## OpenAI 제한 진단
429 응답은 원문 대신 요청/토큰 제한 종류, 허용량·요청량, 재시도 대기 초만 실패 분석의 usage.failure와 단계 로그에 저장합니다. 공유 OpenAI 대기 상태가 있으면 새 유료 요청 없이 대기합니다. 기존 상세 정보 없는 429의 1시간 대기는 최근 실패 후 최소 60초가 지나면 재평가하고, 이후에는 제공자 대기 시간을 사용합니다. API 결제/잔액 변경은 직접 처리합니다.


## 일정 추가·삭제 대조
접속 대조는 미래 일정 신규 등록뿐 아니라 본인의 웹 삭제 표시 및 검토 제외를 Google에 재반영합니다. 삭제 완료 후 내보내기 ID 목록이 비어도 원래 일정의 고정 ID로 재확인하며, Google에서 복원되거나 늦게 생성된 삭제 대상은 다시 삭제합니다. Google 404/410·취소 상태는 삭제 완료로 취급합니다. 테스트 모드·분석 기록 초기화·구독 해제와 무관하게 본인의 기존 내보내기 및 삭제 기록도 대조합니다. 단순히 과거가 됐다는 이유로 기존 일정을 삭제하지 않으며, 웹에서 명시적으로 삭제·제외한 앱 일정만 제거합니다.


## 토큰 절약 (모델 유지)
`gpt-5.4-mini` 모델과 이미지 high 설정은 유지합니다. 완전히 같은 이미지 바이트는 한 요청에 한 번만 보내며 출력은 verbosity low를 사용합니다. 6,000 출력 토큰은 상한으로 유지하고 실제 사용량은 별도로 기록합니다. 테스트 초기화는 수집 위치와 표시 기록을 초기화하지만 동일 회원의 같은 입력(이미지·캡션·계정·게시일·원본 주소·모델·프롬프트 버전)의 완료 결과는 재사용합니다. 새 표시 기록이 필요하면 기존 결과를 복사하고 새 API 사용량을 0으로 저장합니다. 기존 세대 캐시도 검증된 원래 세대와 정확한 해시가 일치할 때만 재사용합니다. 이미지나 캡션 변경은 새 분석입니다. 개인 업로드 결과는 회원 간 공유하지 않습니다. 진행상황의 사용량은 조회된 최근 최대 30건의 측정값으로, 조직 전체 과금액이 아닙니다.

## 휴대폰 캘린더 반영 확인
Google 등록·수정 후 동일 ID를 다시 읽어 관리 필드가 일치할 때만 내보내기를 완료합니다. 삭제 후에도 404/410 또는 cancelled 상태를 재조회합니다. 짧은 반영 지연은 요청 안에서 제한적으로 확인하고, 일치하지 않으면 영속 대기열에 남깁니다. 일시 오류는 30초부터 지수 대기하며 최대 15분으로 제한합니다. 인증·권한 오류는 15분 대기를 유지합니다.

Vercel 배포 API는 대기 작업이 있으면 `waitUntil`로 응답 후 서버 처리를 등록합니다. 회원별 최대 20개와 요청 시작 후 240초 한도를 적용하고 짧은 재시도에는 합계 최대 60초만 기다립니다. 브라우저는 `/api/sync/status`로 상태를 조회하며 후속 처리를 계속 요청할 필요가 없습니다. 브라우저 종료·함수 시간 제한·배포로 처리가 중단돼도 Supabase의 작업을 삭제하지 않으므로 활성 15분 예약 실행이 이어받습니다. `next_due`는 실행 가능한 시각이며 실제 처리는 예약 지연·이전 작업량에 따라 늦어질 수 있습니다. 보안 확인·OAuth 재승인은 사용자 조치가 필요합니다. 서버 작업은 회원별 `/api/sync/background` 이력으로 진행상황과 다운로드 로그에 남깁니다.

삭제가 끝나면 웹이 Google 추가·삭제 대조를 즉시 요청합니다. 대조 시 이미 같은 값인 일정에는 불필요한 PATCH를 보내지 않습니다. Google 반영 확인은 최근 등록 대상과 삭제 대상을 합쳐 최대 10개를 조회하며, 이 결과는 기기 수신 확인을 의미하지 않습니다. `google.write_verified` 로그는 Google 재조회 성공만 뜻합니다.

Google 앱에서 보이는데 삼성 앱에서 보이지 않는 경우 Google 캘린더 → 설정 → 일반 → ‘다른 앱과 Google Calendar 데이터 공유’를 별도로 확인합니다. 이 설정은 이미 캘린더 권한이 부여된 기기 앱들의 Google 일정 접근에 영향을 줍니다. 개별 캘린더 동기화·목록 표시와 다릅니다. Vercel 웹앱은 이 기기 설정을 변경하거나 삼성 앱 내부의 수신을 강제하지 않습니다. 공식 안내: https://support.google.com/calendar/answer/16089827?hl=ko

## Meta 접근 차단 진단
Meta `200/5258005` (`API access blocked`)는 일반적인 대상 계정 조회 오류와 구분합니다. 이 경우 운영자가 Meta 개발자 대시보드의 보안 확인·제한 알림을 먼저 확인해야 합니다. 이 코드만으로 대상이 개인 계정이라고 판단하거나 토큰 재발급으로 해결됐다고 간주하지 않습니다. `meta.http.start/complete/failed` 단계와 HTTP 상태·Meta 코드·하위 코드·오류 분류만 진행상황 및 다운로드 로그에 기록합니다. 토큰·요청 URL·대상 아이디·Meta 원문 오류는 기록하지 않습니다. 연결 설정의 존재는 실제 API 이용 가능 여부와 다르므로 화면에는 ‘자동 수집 연결 설정됨’으로 표시합니다.

## 운영자 회원 일정 조회
`MEMBER_SCHEDULE_ADMIN_IDS`에 명시한 Supabase 회원 UID만 ‘회원 일정’ 메뉴와 `/api/admin/*` 조회 API에 접근합니다. 기존 `OPERATIONS_ADMIN_IDS`만으로는 일정 내용 접근을 허용하지 않습니다. 이번 운영자는 기존에 확인한 프로젝트 소유자 한 명으로 제한합니다. Supabase RLS와 일반 회원 API는 변경하지 않습니다.

회원 이메일을 선택하면 `/api/events`와 같은 개인 분석·구독 공유 분석·본인 내보내기 기록을 20개 분석씩 조회합니다. 검토 제외·삭제 항목도 구분하여 표시하고 등록 후보 판정은 실제 발행 코드와 동일한 `calendarEventPayload` 및 `upcomingPayload`를 사용합니다. 저장된 등록 ID, 대기 작업, 실제 Google 조회 결과는 별도로 표시합니다. Google 확인은 서버에서 계산한 앱 관리 일정 ID에 대한 GET만 수행하며, 기본 캘린더나 임의 이벤트를 조회하거나 일정을 추가·수정·삭제하지 않습니다. 인증 토큰 자동 갱신은 기존 방식으로 암호화 저장됩니다.

목록 조회는 분당 60회, Google 확인은 분당 20회로 제한합니다. 모든 응답은 `no-store`, 회원 이메일·일정 내용·토큰은 진단 로그에 넣지 않습니다. 접근 이력에는 운영자 본인의 요청 경로와 대상 회원의 단방향 해시만 남깁니다. 메뉴는 읽기 전용이며 휴대폰 캘린더 수신 여부를 보증하지 않습니다. 실제 Google 확인은 명시적으로 눌렀을 때만 실행합니다.
